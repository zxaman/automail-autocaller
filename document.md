# AutoCall & AutoMail — Project Requirements

**Document status:** Pre-project requirements draft for review  
**Project stage:** Architecture and documentation only  
**Last updated:** 2026-09-06

## 1. Product Summary

AutoCall & AutoMail is a centralized communication and productivity platform for recruitment, staffing, HR, calling-service, mailing-service, lead-generation, business-development, and sales/outreach teams.

The product combines:

- Contact management
- Excel/CSV import
- Provider-backed in-application calling
- Gmail-based email sending
- Email templates
- Signatures
- Reusable attachments
- Communication history
- Dashboard analytics

The core value proposition is:

> One workspace for your team to import contacts, call them, email them, and track every interaction.

## 2. Business Problem

The current workflow often requires users to move repeatedly between Excel, a phone dialer, Gmail, file storage, and a manually maintained spreadsheet.

Typical workflow today:

```text
Excel
  ↓
Copy phone number
  ↓
Open phone dialer
  ↓
Call candidate or client
  ↓
Open Gmail
  ↓
Copy recipient, subject, body, and attachment
  ↓
Send email
  ↓
Manually update Excel
  ↓
Repeat
```

Problems created by this workflow:

- Repetitive manual copy/paste work
- Missed follow-ups
- No unified communication timeline
- Difficult activity reporting
- Poor manager visibility
- No reliable call and email analytics
- High chance of data-entry errors

## 4. Core User Workflow

```text
1. User signs in with Google.
2. User opens the dashboard.
3. User uploads an XLSX, XLS, or CSV file.
4. Import wizard previews and validates the file.
5. User maps spreadsheet columns to application fields.
6. Contacts are imported and deduplicated.
7. User opens a contact profile.
8. User starts a provider-backed in-application call.
9. User controls and ends the call.
10. User selects Send Follow-up Email.
11. The email composer opens with the contact preselected.
12. User chooses a template, signature, and attachment.
13. A personalized preview is shown.
14. The email becomes an individual queued delivery job.
15. Call and email activity appears in the contact timeline.
16. Dashboard metrics update.
```

### 5.4 Flexible Excel and CSV Import

Supported formats:

- XLSX
- XLS
- CSV

The import process must not depend on exact headers such as `Name`, `Phone`, or `Email`.

The importer must understand variations such as:

- `Phone No.`
- `Phone Number`
- `Mobile`
- `Mobile No`
- `Contact Number`
- `Telephone`
- `Candidate`
- `Candidate Name`
- `Applicant`
- `User`
- `Full Name`
- `Email ID`
- `Mail`
- `Email Address`

Import behavior:

- Normalize headers by removing punctuation, spacing differences, and casing differences.
- Match known aliases and synonyms.
- Inspect sample values to identify phone, email, and name columns.
- Use confidence scoring.
- Automatically map high-confidence fields.
- Require confirmation for ambiguous fields.
- Allow manual mapping and ignoring columns.
- Support files where the first row is not a header.
- Support first name plus last name combination.
- Detect duplicate headers and blank columns.
- Preserve source headers and mappings in the import batch.
- Show row-level validation errors.
- Allow a configurable default phone country.
- Handle Excel numeric/scientific notation issues where possible.

Default mapping behavior:

- Name is required.
- At least one of phone or email is required for a usable contact.
- Phone and email validation errors are reported per row.
- Generic headers such as `Number`, `User`, or `Details` must not be trusted without value analysis.

Import wizard steps:

```text
Upload → Preview → Map Columns → Validate → Review → Import → Result
```

Import result must report:

- Total rows
- Imported rows
- Duplicate rows
- Invalid rows
- Skipped rows
- Missing-name rows
- Invalid-phone rows
- Invalid-email rows
- Detailed row errors

### 5.5 Import Batches

- Total rows
- Successful rows
- Duplicate rows

- Validation errors

### 5.6 AutoMail

The MVP email integration uses:

- Gmail address
- Google-generated Gmail App Password
- Gmail SMTP
- Nodemailer

The system must never ask for or store a normal Gmail password.

Email account features:

- Add Gmail account
- Verify SMTP credentials
- Send test email
- Set default account
- Replace credentials
- Disconnect account
- Display connected status without displaying credentials

Email composer fields:

- From
- To
- CC
- BCC
- Subject
- Body
- Template
- Signature
- Attachments

### 5.7 Email Templates

Users can:

- Create templates
- Edit templates
- Delete templates
- Duplicate templates
- Preview templates
- Use templates

Supported variables include:

```text
{{name}}
{{email}}
{{phone}}
{{company}}
{{designation}}
{{senderName}}
{{senderEmail}}
```

Variables are rendered separately for each recipient.

### 5.8 Signatures

Users can configure:

- Multiple signatures
- Default signature
- HTML signature
- Plain-text signature
- Optional logo/image

The selected signature is applied automatically and should not require manual copy/paste.

### 5.9 Reusable Attachments

Users can upload and reuse files such as:

- Job descriptions
- Company profiles
- Interview processes
- Offer documents
- Brochures

Large files must be stored in private object storage. MongoDB stores file metadata only.

### 5.10 Email Queue and History

For multiple recipients, the system creates separate email jobs.

The system must not place all recipients in one visible `To` field.

Email statuses:

```text
Draft → Queued → Sending → Sent
                         ↘ Failed
```

The queue must support:

- Throttling
- Retry for temporary provider failures
- Permanent failure handling
- Per-recipient progress
- Idempotency
- Account-level pause on authentication failure
- Gmail-limit awareness

Email history must show:

- Recipient
- Contact
- Sender account
- Subject
- Attachments
- Date
- Status
- Failure reason where applicable

### 5.11 AutoCall

Calling must use an actual provider-backed in-application architecture.

The product must not use `tel:` or the device dialer as the production calling implementation.

The calling screen should support, where available:

- Initiating
- Ringing
- Connected
- On hold
- Muted
- DTMF
- Speaker/audio route
- Recording indicator
- Ending
- Completed
- Failed
- Duration timer

The first provider candidate is Twilio Voice, subject to country availability, pricing, account approval, and regulatory review. Telnyx or Vonage may be substituted behind the provider abstraction.

### 5.12 Call History and Queue

Call history displays:

- Contact
- Phone number
- Direction
- Status
- Date and time
- Duration
- Recording availability

The calling queue is user-controlled and sequential. The application must not automatically place hundreds of calls without explicit user action.

### 5.13 Unified Communication Timeline

The timeline combines:

- Calls
- Emails
- Notes
- Recordings
- Attachments
- Import activity

After a call completes, the user can open a follow-up composer prefilled with the contact's email address.

## 7. Non-Goals for the Initial MVP

The first MVP will not attempt to provide:

- Unlimited bulk email
- Spam or provider-limit bypassing
- Silent call recording
- Fake telephony functionality
- Unsupported native mobile behavior
- Full marketing automation
- Complex multi-company billing
- Predictive lead scoring
- A full accounting or ATS replacement

## 8. Product Quality Requirements

The product must be:

- Secure by default
- Responsive on desktop and mobile
- Accessible
- User-isolated
- Auditable
- Observable
- Testable
- Modular
- Compatible with future teams
- Honest about provider and platform limitations
